## 第一章 总则

### 第一条（立法目的）
为建立**可追溯、可审计、不可篡改**的软件版本管理体系，确保系统版本号准确反映代码变更实质，维护 Git 历史完整性与不可否认性，根据《§14 强制开发12步骤独立约束规则》与《规则治理与一致性规范》，制定本条例。

### 第二条（适用范围）
本条例适用于 MTSCOS AI 项目的所有**代码仓库版本号管理活动**，包括但不限于：Flask 服务、AI 引擎、daemon、前端资源、数据库迁移脚本、部署配置。

### 第三条（版本权威源 · 单一事实来源）
系统版本号的**唯一权威源**为 `flask-app/VERSION` 文件（纯文本，允许前导 `v` 与可选 tag 后缀），由 `flask-app/core/version_source.py` 读取。**禁止**在源码中以字符串常量硬编码版本号，违者依第十五条论处。

### 第四条（SemVer4 格式规范）
系统版本号采用四段语义化格式：

```
v<major>.<minor>.<patch>.<build>[-<tag>]
```

| 段 | 中文 | 取值范围 | bump 条件 | bump 后低位归位 |
|----|------|----------|-----------|----------------|
| major | 主版本号 | 1–99 | 不兼容 API 变更 / 重大架构重构 / 核心模型替换 | 全部归 0 |
| minor | 次版本号 | 0–99 | 新增向后兼容功能/模块/子系统 | build 归 0 |
| patch | 修订号 | 0–999 | Bug 修复 / 安全加固 / 小优化（不改变 API 契约） | build 归 0 |
| build | 构建序号 | 0–9999 | **默认自动升级目标** · 日常迭代/配置/文案/测试 | 自增不归位 |
| tag | 代号（可选） | 自由文本 | 发布代号如 `-iceberg-saga`，从 VERSION 文件完整读取 | — |

### 第五条（历史版本兼容）
历史三段版本号（`MAJOR.MINOR.PATCH`）在运行时解析时**自动补 build=0**，不触发版本比较错误。历史 commit 中的三段版本标签不要求回填。

## 第二章 升级规则

### 第六条（BUILD 自动升级 · 默认行为）
系统检测到以下任何一类变更时，自动 bump build 段（**最小影响面原则**）：
1. 代码文件修改（非破坏性）
2. 配置参数调整
3. 文案/注释/文档更新
4. 测试用例增删改
5. daemon 参数调优
6. 依赖版本锁定（非升级）

**执行主体**: sys_rule_enforcer daemon（每 300s）
**记录义务**: bump 后 60s 内必须在 mt_rule_changelog INSERT 一条记录
**无需 SA 介入**

### 第七条（PATCH 升级）
系统检测到以下条件之一且满足第六条全部条件时，自动 bump patch + build 归 0：
1. bug fix commit ≥ 3 条 / 24h
2. 安全事件（mt_eigenflux_comm_messages 安全告警 ≥ 3 条 / 24h）
3. mt_permission_audit_detail 新增越权案例 ≥ 5 条 / 7d
4. VIKEY 加密狗固件升级
5. auto_evolution 连续失败 ≥ 3 次 / 24h

### 第八条（MINOR 升级）
系统检测到以下条件之一时，bump minor + 低位全部归 0：
1. 新增完整模块/子系统（≥ 500 行核心代码）
2. mt_andromeda_rule_knowledge chunk 新增 ≥ 50 条 / 7d
3. EigenFlux 演化日志新增 ≥ 100 条 / 7d
4. 仙女座 AI 审计师评估 ≥ "可扩展" 级

**前置义务**: MINOR bump 必须附带 EigenFlux 5 人磋商记录
**执行主体**: auto_evolution → sys_rule_enforcer 联合

### 第九条（MAJOR 升级 · 重大架构变更）
仅当同时满足以下全部条件时，方可 bump major：
1. git commit message 包含 `BREAKING CHANGE:` 标记
2. API 变更不兼容（REST 接口路径/参数/返回值变更）
3. **SA 手动批准** + VIKEY 实时检测
4. EigenFlux 5 人磋商**一致通过**（≥ 4/5）
5. mt_rule_changelog.approved_by_7step = 1

**违反 MAJOR bump 前置条件 → 自动拦截 + mt_iron_rule_violations 落库**

### 第十条（降级规则 · 版本号减小）
系统版本号**不得**降级（减小）。如因严重事故必须降级，需同时满足：
1. SA VIKEY 实检（sa_vikey_verified = 1）
2. EigenFlux 5 人紧急磋商（必须全票通过）
3. mt_iron_rule_violations 新增一条
4. evolution_log 记录 trigger_type = 'version_downgrade'
5. Git 历史保留，不得 `git reset --hard` 回退

违反任何一步 → **fail-closed** + mt_rule_violation_alert(alert_type='VERSION-DOWNGRADE-NOT-VIKED')

### 第十一条（版本 bump 冲突解决）
同一时间段内多个版本 bump 请求冲突时，按以下优先级执行：
1. MAJOR > MINOR > PATCH > BUILD
2. 安全事件触发的 PATCH > 普通 PATCH
3. 先到先服务（同一级别）

## 第三章 运行时派生义务

### 第十二条（禁止硬编码版本号）
除 `flask-app/VERSION` 文件与 `VERSION` git tag 外，**禁止**在源码的任何位置以字符串常量（如 `'v24.0.0-iceberg-unified'`）硬编码系统版本号。所有模块**必须**通过以下接口派生版本：
- `core.version_source.read_raw_version()` — 完整含 tag
- `core.version_source.get_system_version()` — 四段核心
- `core.version_source.get_version_info()` — dict 含 major/minor/patch/build/tag

**拦截层**: pre_commit hook → grep 扫描 `'v\d+'` / `"v\d+"` 模式 + VERSION 文件比对 → 不一致则 exit 1

### 第十三条（版本漂移检测）
CI 流水线每 1000 轮必须执行版本漂移自检：
1. `grep -rn 'v2[0-9]\|v1[0-9]\|SYSTEM_VERSION' flask-app/ --include=*.py`
2. 结果与 `flask-app/VERSION` 比对
3. 不一致 → CI 红色阻断合并
4. 同时落库 mt_rule_integrity_scan(issue_type='VERSION-DRIFT')

## 第四章 罚则

### 第十四条（罚则总则）
违反本条例任何一条，根据情节轻重承担对应法律后果。**本条例罚则与 §14 IRON_RULE 九铁律、《机密等级与访问控制规范》fail-closed 机制联动执行**。

### 第十五条（硬编码版本号处罚）
| 情节 | 认定 | 处罚 |
|------|------|------|
| 单处硬编码 | 首次 | pre_commit 拦截 + rule_violation_alert 落库 + 仙女座弱约束词扫描 |
| 多处硬编码（≥3 处） | 从重 | CI 流水线红色 + mt_iron_rule_violations 落库 + SA 审批 |
| 故意漂移（version 与 VERSION 文件差 ≥ minor） | 恶意 | **fail-closed** · Flask 拒绝启动 · 强制 restore from git |

### 第十六条（非法 bump 处罚）
| 行为 | 处罚 |
|------|------|
| MAJOR bump 无 EigenFlux 磋商 | mt_iron_rule_violations + 禁止 push 14 天 |
| 降级无 VIKEY 实检 | **fail-closed** · 锁容器 · SA 立即介入 |
| BUILD/MINOR/PATCH bump 无 changelog | before_request 拦截 (403) + rule_violation_alert |
| 禁用版本 bump 自动闭环 | 仙女座自动 fail-closed + daemon 心跳中断 |

### 第十七条（不诚信认定）
以下行为按"阻碍版本治理"认定，处罚加倍：
1. 删除/篡改 mt_rule_changelog 记录
2. `git reset --hard` 回退已发布版本（非 MAJOR bump 审批场景）
3. 修改 version_source.py 返回伪造版本号
4. 在 `.git/hooks/` 中绕过 pre_commit 版本检查

## 第五章 立法与修订

### 第十八条（立法程序）
本条例由**立法委 · 常务委员会**提出，经 7 步审批流程后生效（§14）。

### 第十九条（修订规则）
| 修订类型 | 示例 | 触发条件 | 审批 |
|---------|------|----------|------|
| MINOR 修订 | v1.2.0 → v1.3.0 | 新增条款（SemVer4 BUILD 自动升级） | EigenFlux 5人磋商 ≥4/5 + SA终审 |
| MAJOR 修订 | v1.3.0 → v2.0.0 | 架构性重写（增强罚则/结构法典化） | 同上 + 立法委全员表决 |
| PATCH 修订 | v2.0.0 → v2.0.1 | 错别字/格式修正 | SA 批准即可 |

### 第二十条（追溯效力）
本条例**不溯及既往**——v1.3.0 修订前的三段版本标签不要求回填，但 **v2.0.0 生效后所有新代码必须遵守 SemVer4**。

### 第二十一条（旧版本兼容与失效）
- 旧规则 §3.1 V-01（三段强制条款）已由本条取代，**自动失效**
- 版本号解析函数 `version_source.parse_version()` 对历史三段版本自动补 build=0，不触发升级
- Git 历史中已存在的三段 tag（如 `v24.0.0`）**不要求**强制重写（filter-repo 代价过大）
